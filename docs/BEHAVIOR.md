# Tokenizer behavior — supported, unsupported, divergent

Reference: SQLite trunk `f879fb1`, `src/tokenize.c`
(`sqlite3GetToken`). The differential test (`make diff`,
`src/tokenizer/t/04_differential_test.co`, 123 corpus inputs) compares type, byte
start and byte length against the C function itself, not against
this document — where they disagree, the harness wins.

## Supported (verified against the C tokenizer)

- All 186 token types with SQLite's exact numeric values
  (`docs/TOKEN_MAP.md`), and all 147 keywords of a default build,
  case-insensitively (`keywordhash.h` as generated by
  `tool/mkkeywordhash.c`).
- Whitespace runs as a single `TK_SPACE`, including the quirk set
  {tab, LF, VT, FF, CR, space} *inside* a run; a UTF-8 BOM
  (EF BB BF) is `TK_SPACE` of length 3.
- Comments: `--` to end of line, `/* … */`; an unterminated block
  comment is `TK_COMMENT` to end of input; `/*` at the very end of
  input is `TK_SLASH` followed by `TK_STAR` (the C code only enters
  the comment path when a byte follows the `*`).
- Identifiers: letters, digits, `_`, `$` and bytes ≥ 0x80 as
  continuation characters; a keyword-shaped run followed by a
  non-keyword identifier character (digit, `$`, ≥ 0x80) is one
  `TK_ID`. First characters `Y`, `Z`, `_`, `x` never start a
  keyword.
- Quoted identifiers: `"…"`, `` `…` `` with doubled-delimiter
  escapes, `[…]`; closed → `TK_ID`, unterminated → `TK_ILLEGAL`.
- String literals `'…'` with `''` escapes; unterminated →
  `TK_ILLEGAL`.
- Blob literals `x'…'` / `X'…'`: hex digits only, even count;
  anything else scans to the next `'` as one `TK_ILLEGAL`.
- Numbers: decimal integers, `0x` hex (requires a hex digit next),
  floats with `.` and/or exponent (exponent requires a digit, or a
  sign and a digit, after `e`/`E`); `_` digit separators anywhere in
  a digit run make the token `TK_QNUMBER` (placement validation is
  the parser's job, as in C); any number directly followed by
  identifier characters absorbs them into one `TK_ILLEGAL`.
- Bind parameters: `?`, `?NNN`, `:name`, `@name`, `#name`,
  `$name`, `$name::suffix`, and the Tcl form `$name(...)`; a bare
  prefix with no name is `TK_ILLEGAL`; a Tcl form whose scan hits
  whitespace before `)` is `TK_ILLEGAL` up to that whitespace.
- Operators/punctuation: the full set from `tokenize.c`, including
  `->`/`->>` → `TK_PTR`, `==` → `TK_EQ`, `<>`/`!=` → `TK_NE`,
  `||` → `TK_CONCAT`, `%` → `TK_REM`, and `!` or a leading VT or
  any other unmatched byte → `TK_ILLEGAL`.
- Byte offsets and lengths are exact for all of the above
  (multibyte UTF-8 identifiers and strings measured in bytes, not
  characters — see the `café` / `αβ` / emoji cases in the tests).

## Known divergences and limits

1. **Valid UTF-8 input only.** The port scans the string's
   bytes directly (`sql.byte_array()`), exactly like the C code;
   for valid UTF-8 this is byte-exact, at every byte offset.
   Invalid UTF-8 byte sequences cannot be represented in a Come
   string at all, so SQLite's byte-level treatment of them (each
   byte ≥ 0x80 is an identifier character) cannot be reproduced.
2. **Embedded NUL is unrepresentable.** A Come string cannot hold
   a NUL character, so "end of input" is the string's end. In C,
   an embedded NUL terminates the token scan (`TK_ILLEGAL`, 0) and
   the parser driver reacts; that situation cannot arise here.
3. **Parser-driver behavior is out of scope, as in C.**
   `sqlite3GetToken` itself returns `TK_ILLEGAL`/0 at end of input
   and raw `TK_WINDOW`/`TK_OVER`/`TK_FILTER` codes;
   `sqlite3RunParser` is what synthesizes `TK_SEMI`/EOF and
   reclassifies those three keywords by lookahead. Both belong to
   step 2 (the parser), not to this port — but callers of this
   tokenizer should know the raw codes are what they get.
4. **`WITHIN` is `TK_ID`, deliberately.** `mkkeywordhash.c` lists
   WITHIN but gates it behind the ORDERSET feature, which a default
   build does not define; the generated table — and therefore this
   port — does not recognize it. Pinned by a regression test.
